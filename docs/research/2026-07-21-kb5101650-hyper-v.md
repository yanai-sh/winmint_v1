# KB5101650 vs Hyper-V / vTPM Start-VM failures (2026-07-21)

**Question:** Does Windows 11 July 2026 cumulative update KB5101650 (OS builds 26200.8875 / 26100.8875) have documented Hyper-V, vTPM, or VM worker-process (`0x800705B4`) regressions?

**Host context (for this note only):** Surface Laptop 7 ARM64, Windows 11 25H2 build 26200.8875, installed KB5101650 and KB5100998 on 2026-07-20. Symptom: Hyper-V Gen2 `Start-VM` with `Enable-VMTPM` fails ~20s with worker timeout `0x800705B4`; `Start-VM` without vTPM succeeds.

**Method:** Prefer Microsoft Support KB pages and Learn release-health known/resolved issues. Community Q&A is cited only as historical pattern, not as product acknowledgment.

---

## Verdict

**No.** As of 2026-07-21, **no primary Microsoft source links KB5101650 (or sibling July packages KB5100998 / KB5121767) to Hyper-V Gen2 Start-VM failures, vTPM enablement failures, or Hyper-V worker-process timeout `0x800705B4`.**

Temporal correlation on this host is real (symptom observed after 2026-07-20 installs). Documented causation for this KB is **not** established.

## What Microsoft documents for KB5101650

### Known issues (KB page)

KB5101650 states:

> Microsoft is not currently aware of any issues with this update.

Source: [KB5101650 — Known issues](https://support.microsoft.com/en-us/servicing/os/windows-11/2026/07/july-14-2026-kb5101650-os-builds-26200-8875-and-26100-8875)

### Documented July regression path (not Hyper-V)

The only widely documented client regression tied to the July LCU **offer path** is:

- **Some Dell devices** with an **Intel Innovation Platform Framework (Intel IPF)** driver can show Device Manager warnings and performance / power / behavior changes after the June 23 preview (**KB5095093**).
- Microsoft temporarily **did not offer KB5101650** to those affected Dell devices.
- Fixed by OOB **KB5121767** (and later updates); hotpatch sibling **KB5121768** for hotpatch-enrolled devices.

Sources:

- [Windows 11 25H2 known issues — Dell / Intel IPF](https://learn.microsoft.com/en-us/windows/release-health/status-windows-11-25H2)
- [Windows 11 24H2 known issues](https://learn.microsoft.com/en-us/windows/release-health/status-windows-11-24H2)
- [Resolved issues — Windows 11 25H2](https://learn.microsoft.com/en-us/windows/release-health/resolved-issues-windows-11-25H2)
- [KB5121767](https://support.microsoft.com/en-us/servicing/os/windows-11/2026/07/kb5121767-out-of-band)

**Explicit gap:** release-health summaries for 25H2 around July 2026 list WSUS sync degradation and the Dell/Intel IPF issue. They do **not** list Hyper-V, vTPM, or `0x800705B4` worker timeouts.

**Host fit:** Surface Laptop 7 ARM64 (Snapdragon) is outside the documented Dell + Intel IPF affected class. KB5121767 is therefore **not** a documented fix path for this symptom.

### Virtualization-adjacent claims (improvements, not regressions)

KB5101650 itself highlights Secure Boot certificate targeting, RDP security (SHA-2 thumbprints), TDI transport hardening, curl 8.21.0, OLE/Office launch fixes, Recycle Bin dialog fixes, and related quality items — **not** Hyper-V Start-VM / vTPM.

Source: [KB5101650 — Improvements](https://support.microsoft.com/en-us/servicing/os/windows-11/2026/07/july-14-2026-kb5101650-os-builds-26200-8875-and-26100-8875)

Because KB5101650 includes the June preview, the closest **virtualization** wording on a primary KB page is in **KB5095093**:

- Networking for virtualized environments: Confidential VMs default to SR-IOV acceleration; **a nested Hyper-V virtualization network setup configuration issue was corrected** for reliable VM **network** provisioning.
- **WSL:** improved mirrored networking mode with VPNs.

Source: [KB5095093 — Networking / WSL](https://support.microsoft.com/en-us/servicing/os/windows-11/2026/06/june-23-2026-kb5095093-os-builds-26200-8737-and-26100-8737-preview)

Those are framed as **fixes/improvements**, not as known Start-VM / vTPM regressions, and they do not mention worker timeout `0x800705B4`.

## Correlation vs causation (this host)

| Factor | Assessment |
|--------|------------|
| Time correlation | **Present** — symptom noted after KB5101650 + KB5100998 on 2026-07-20 |
| Documented KB→vTPM Start-VM link | **Absent** in Microsoft KB / release-health primary sources |
| Match to documented July known issue | **No** — published July client issue is Dell + Intel IPF; this host is Surface Laptop 7 ARM64 |
| Symptom specificity | **Strong local signal** — fails only with vTPM; succeeds without — points at vTPM / key-protector / host TPM trust path, not “Hyper-V entirely broken” |
| Causation by KB5101650 | **Unproven** — treat as hypothesis until bisect / rollback / event-log evidence isolates the LCU |

**Conclusion for this host:** correlation only. Do not treat KB5101650 as a confirmed Hyper-V regression without further verification. Do not expect KB5121767 to address this symptom based on published notes.

## Recommended next verification steps

1. **Capture evidence before changing packages**
   - Event Viewer: `Microsoft-Windows-Hyper-V-VMMS-Admin` (e.g. 15500 / 15130) and `Microsoft-Windows-Hyper-V-Worker-Admin` around the ~20s failure.
   - Confirm exact message text includes worker timeout `0x800705B4`.
   - Record `Get-ComputerInfo` / `winver` build, `Get-Tpm`, Secure Boot state, and whether host TPM is ready.

2. **Isolate vTPM trust configuration (non-destructive first)**
   - On a disposable Gen2 VM: `Disable-VMTPM` → `Set-VMKeyProtector -NewLocalKeyProtector` → `Enable-VMTPM` → `Start-VM` (community recovery pattern for corrupted key protectors; not a Microsoft KB5101650 fix).
   - Compare brand-new Gen2 VM with vTPM vs without.

3. **Bisect the July packages if feasible**
   - Uninstall **KB5101650** alone (leave KB5100998) or use Point-in-time Restore / restore point from before 2026-07-20, then retest Start-VM with vTPM.
   - Reinstall LCU only if the bisect clears the symptom — that is the minimum bar for “KB caused it” on this machine.
   - Do **not** treat optional KB5121767 as the fix candidate unless the host somehow matches the Dell/Intel IPF issue (unlikely on SL7 ARM64).

4. **Platform checks specific to SL7 ARM64**
   - Latest Surface firmware / UEFI; confirm virtualization / TPM settings unchanged.
   - Rule out host TPM busy/locked state and third-party AV injecting into `vmwp` / `vmcompute` (older Microsoft guidance exists for compute-process DLL policy issues — different error class, still worth checking).

5. **Watch primary channels**
   - Re-check [25H2 known issues](https://learn.microsoft.com/en-us/windows/release-health/status-windows-11-25H2) and [KB5101650](https://support.microsoft.com/en-us/servicing/os/windows-11/2026/07/july-14-2026-kb5101650-os-builds-26200-8875-and-26100-8875) if Microsoft later adds a Hyper-V/vTPM known issue.
   - File Feedback Hub with VMMS/Worker logs if bisect implicates the LCU.
